### 💿 1. ORU (오루) — Music Review & Community
> **개발 기간:** 2025.10 ~ 현재 (진행 중)  
> **서비스 소개:** 앨범 단위 리뷰, 커뮤니티 게시판, 오늘의 앨범 등 음악 감상 기록과 리스너 간의 취향 교감을 제공하는 웹 서비스

| 구분 | 정보 |
| --- | --- |
| **인원 구성** | 총 3명 (**본인 참여도: DB 설계 30%, 개발 50%**) |
| **Tech Stack** | `TypeScript`, `Next.js (App Router)`, `Supabase`, `PostgreSQL`, `Vercel` |

#### 👨‍💻 담당 업무 및 핵심 성과
- **풀스택 아키텍처 설계:** Next.js 및 Supabase를 활용하여 음악 데이터 탐색 인프라 구축 및 확장성 있는 리뷰 CRUD API 전담 개발
- **실시간 데이터 파이프라인 구축:** 유저 평점 및 피드 데이터를 실시간으로 집계하고 연동하는 결합 로직 구현
- **인프라 및 배포 최적화:** NextAuth.js 기반 인증 환경 설계 및 Vercel(icn1 리전)을 통한 지연 시간 최소화 배포 운영

#### 📊 가치 입증 및 트러블 슈팅 (Problem-Solving)

##### 🛠️ 이슈 1: 무분별한 새로고침 및 본인 게시글 조회수 어뷰징으로 인한 데이터 신뢰도 저하
- **문제 정의:** 사용자가 새로고침(F5)을 연타하거나 본인 글을 반복 조회하여 조회수를 비정상적으로 올리는 어뷰징 취약점 발견. 이로 인해 트렌딩 게시글의 데이터 신뢰도가 떨어지고 불필요한 서버 자원이 낭비됨.
- **가설 수립:** 프론트엔드단에서 세션 기반으로 1차 진입 여부를 차단하고, 서버단에서 요청 유저와 작성자 ID를 검증하면 데이터 정밀도를 확보하면서 서버 자원 소모를 최소화할 수 있을 것이다.
- **액션 및 검증:** - `sessionStorage`를 활용해 클라이언트 레벨에서 중복 방문 시 API 요청을 발생시키지 않도록 미들웨어 로직 구현.
  - 백엔드 API 내에 로그인 세션 ID(`NextAuth`)와 게시글의 `author_id`를 비교·검증하는 로직을 추가하여 작성자 본인의 조회는 카운트에서 제외 처리.
- **결과 및 러닝 포인트:** 무분별한 어뷰징을 완전히 차단하여 게시판 데이터의 정량적 신뢰성을 확보함. **[성공 기준: 인위적 조회수 조작율 0%]** 클라이언트와 서버의 역할을 적절히 분배하여 유효한 요청만 처리하는 방어적 설계의 중요성을 체득함.

##### 🛠️ 이슈 2: 이종 외부 음원 API 동시 호출 시 병목으로 인한 검색 성능 저하
- **문제 정의:** 복수의 외부 음원 공급사 API로부터 데이터를 받아오는 과정에서 순차적(Waterfall) 호출이 발생하여, 검색 속도가 지연되고 UI가 멈추거나 깨지는 현상 발생.
- **가설 수립:** 외부 API 호출을 비동기 병렬 처리로 전환하고 프론트엔드로 전달하기 전 단일 포맷으로 가공하는 결합 레이어(Adapter Pattern)를 도입하면, 응답 시간을 단축하고 UI 안정성을 확보할 수 있을 것이다.
- **액션 및 검증:**
  - `Promise.all`을 도입하여 각 API 요청을 병렬로 동시에 처리하도록 백엔드 로직 수정.
  - 가공되지 않은 다형성 데이터를 표준 스펙에 맞추어 통합하는 내부 결합 레이어를 구축하여 프론트엔드의 렌더링 비용을 감소시킴.
- **결과 및 러닝 포인트:** 기존 대비 검색 응답 속도를 대폭 개선하여 끊김 없는 사용자 경험(UX)을 완성함. 분산된 외부 데이터 소스를 안전하게 통합하고 제어하는 데이터 파이프라인 설계 역량을 강화함.

- **문제 정의:** 다수의 유저가 실시간 퀴즈 대전에 동시 진입할 때, 대용량 정답 데이터 전송 병목이 일어나 유저 간 타이머 및 문제 출제 화면의 싱크가 맞지 않는 치명적인 동기화 오류 발생.
- **가설 수립:** 데이터베이스 채널 전송 단위를 핵심 페이로드(Payload) 정보로 최소화하고, 실시간 알림(Subscription) 구독 범위를 세분화하면 네트워크 오버헤드가 줄어들어 동기화 지연을 해결할 수 있을 것이다.
- **액션 및 검증:**
  - 전역 상태로 관리되던 원본 데이터 구독 방식을 화면 전환 및 정답 여부에 필요한 최소한의 메타데이터 구독 방식으로 변경.
  - 클라이언트 브로드캐스팅 주기 최적화 및 패킷 크기를 경량화하여 네트워크 트래픽 부담을 해소함.
- **결과 및 러닝 포인트:** 유저 간 실시간 화면 동기화 오차를 무시할 수 있는 수준으로 좁히며 공정한 대전 환경 구축에 성공함. **[성공 기준: 동시 접속 시 동기화 오차 범위 내 도달]** 실시간 아키텍처 환경에서는 데이터 레이어의 '다이어트'가 성능에 직결된다는 큰 러닝 포인트를 얻음.

#### 📊 가치 입증 및 트러블 슈팅 (Problem-Solving)

##### 🛠️ 이슈 1: 캘린더 내 대량의 일정 데이터 로딩 시 렌더링 병목 및 화면 버벅임 현상
- **문제 정의:** 스터디 누적 일정이 많아짐에 따라 fullCalendar 컴포넌트가 모든 데이터를 한 번에 파싱 및 조회하면서 로딩 시간이 길어지고, 드래그 앤 드롭 시 화면이 심하게 끊기는 현상 발생.
- **가설 수립:** 렌더링에 불필요한 무거운 데이터 필드를 백엔드 쿼리 단에서 제외하고 뷰포트(Viewport) 기반 요청 구조로 변경하며, React 렌더링 주기를 제어하면 부드러운 스크롤 성능을 확보할 수 있을 것이다.
- **액션 및 검증:**
  - 기존 `SELECT *` 형태의 묵시적 조회를 필요한 핵심 데이터(일정 제목, 시작/종료일, ID)만 추출하도록 MyBatis 매퍼 쿼리 튜닝.
  - 프론트엔드 단에서 불필요하게 상태(State)가 업데이트되어 화면이 리렌더링되는 빈도를 `useMemo` 및 디바운싱 기술을 통해 제어.
- **결과 및 러닝 포인트:** 대량의 데이터를 핸들링할 때도 캘린더 조작 성능 및 로딩 속도를 초기 대비 눈에 띄게 개선함. **[성공 기준: 스케줄 조작 인터랙션 프레임 드랍 제거]** 무조건적인 데이터 전달보다 프론트엔드와 백엔드가 서로 교감하는 '최적의 데이터 스펙 정의'가 중요함을 배움.
